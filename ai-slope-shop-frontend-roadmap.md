# AI Slop Shop: Frontend Roadmap

Статус: каталог подключён к InsForge и работает в production; оптимизация изображений через `next/image` проверена на Vercel, quantity работает, общий header и отдельная страница избранного добавлены.

Текущий следующий шаг: **очистить детальную страницу товара: убрать `SLUG / ID`, перенести `Back to catalog` выше контента и добавить действие favorites под кнопкой корзины**.

Цель: превратить текущий React Shop Lab в компактный, аккуратный магазин фантастических AI-товаров без лишних разделов, рекламы, sidebar и декоративного шума.

Рабочее название: **AI Slop Shop**.

Слоган: **Невозможные товары для сомнительной реальности**.

## Принципы

- Сначала исправляем поведение, потом полируем внешний вид.
- Не добавляем функцию только ради количества функций.
- Все 47 товаров пока загружаются одним списком.
- Видимой пагинации не будет.
- Компоненты `entities` показывают данные, а пользовательские действия принадлежат `features`.
- Нижняя граница количества должна защищаться не только в кнопках, но и в reducer; искусственного верхнего лимита нет.

## Этап 1. Рабочий quantity на странице товара

### Задача

Сейчас селектор `- 1 +` в `ProductDetails` только выглядит интерактивным. Нужно связать выбранное количество с добавлением в корзину.

### Архитектура

Создать feature-компонент уровня корзины, например:

```txt
src/features/cart/ui/AddToCartControl.tsx
```

Он владеет локальным `quantity` и содержит:

- кнопку уменьшения;
- текущее количество;
- кнопку увеличения;
- кнопку `Add to cart`.

`ProductDetails` не должен владеть состоянием корзины. Из него нужно убрать декоративный quantity selector, а готовый `AddToCartControl` передавать через существующий `actions` slot.

### Изменения модели корзины

- `addToCart` принимает `product` и `quantity`.
- action `add` содержит выбранное количество.
- новый товар добавляется с выбранным количеством.
- если товар уже есть, выбранное количество прибавляется к существующему.
- выбранное количество не может быть меньше `1`.

### UI-правила

- `-` disabled при `quantity === 1`;
- обе кнопки имеют понятные `aria-label`;
- disabled визуально заметен и не выглядит кликабельным;
- после добавления quantity можно оставить выбранным или вернуть к `1`, но поведение должно быть единообразным.

### Зачёт

- Можно выбрать 1, 2 или больше единиц товара.
- В корзину попадает именно выбранное количество.
- Повторное добавление увеличивает существующую позицию.
- Нельзя получить `0` или отрицательное количество.

## Этап 2. Корректное управление количеством в корзине

### Что изменить

- При количестве больше `1` кнопка минуса уменьшает количество на единицу.
- Уменьшение с `1` удаляет позицию из корзины.
- Отдельная кнопка `Remove` остаётся быстрым явным способом удаления.
- Кнопка плюса увеличивает количество на единицу без искусственного потолка `99`.
- Reducer не допускает нулевого или отрицательного количества в сохранённой позиции.

### Почему проверка нужна в двух местах

UI объясняет поведение пользователю. Reducer защищает состояние, если action будет вызван из другого компонента или после будущего рефакторинга.

### Зачёт

- Сохранённая позиция всегда имеет положительное количество.
- Уменьшение с `1` предсказуемо удаляет позицию.
- `Remove` и `Clear cart` продолжают работать.
- Persistence и синхронизация вкладок не ломаются.

## Этап 3. Общий header и страница избранного

Статус: общий `SiteHeader`, поисковый slot каталога и маршрут `/favorites` реализованы. Оставшиеся изменения детальной страницы вынесены в следующий пункт ближайшего порядка работы.

### Задача

Сохранить компактную шапку магазина не только в каталоге, но и на детальной странице товара. Навигация должна выглядеть как единая часть приложения, а не как отдельная marketing-панель каждого маршрута.

### Состав общего header

```txt
AI Slop Shop | Favorites | Cart (3)
```

- Название является `Link` на `/`.
- `Favorites` ведёт на `/favorites` и может показывать количество сохранённых товаров.
- `Cart` ведёт на `/cart`.
- Рядом с корзиной показывается `totalCount`.
- Состав навигации не меняется между маршрутами: текущий раздел не скрывается, а получает спокойное активное состояние и `aria-current="page"`.
- На странице корзины ссылка `Cart` остаётся на привычном месте; на странице избранного так же остаётся `Favorites`. Это сохраняет стабильную геометрию header.

### Каталоговые элементы

- Поиск передаётся в `SiteHeader` через optional slot и отображается только в каталоге.
- Старый `CatalogHeader` удалён; каталог использует отдельный `CatalogSearchSlot`.
- Автофокус поиска не должен переноситься в общий header и срабатывать на странице товара, корзины или избранного.
- `Back to catalog` не является глобальной навигацией: на странице корзины он удалён, а на детальной странице будет перенесён ближе к header.
- Header компонуется на уровне маршрутов: каталог передаёт поисковый slot, остальные страницы используют тот же компонент без slot.

### Страница `/favorites`

- Показывает ту же сетку `ProductCard`, но только для ID из `favoritesStore`.
- Favorites продолжают храниться в `localStorage`; backend, authentication и поле `isLiked` в товарах не добавляются.
- Пустое состояние объясняет, как добавить товары, и даёт ссылку обратно в каталог.
- Удаление из избранного сразу убирает карточку из списка без искусственной задержки.

### Детальная страница товара

- Убрать из пользовательского интерфейса технический блок `SLUG / ID`.
- Перенести `Back to catalog` выше основного блока товара, ближе к header, и оформить компактной ссылкой.
- Под `Add to cart` добавить самостоятельное действие `Add to favorites` / `Remove from favorites` с текущим состоянием сердца.
- Оставить quantity selector непосредственно над `Add to cart`.
- Не дублировать header внутри `ProductDetails`: общая навигация должна принадлежать layout или общему композиционному компоненту маршрута.

Использовать клиентскую навигацию Next.js через `Link`, без принудительной полной перезагрузки страницы.

### Зачёт

- Из любого маршрута можно вернуться в каталог.
- Из header можно открыть отдельную страницу избранного.
- Счётчик корзины обновляется сразу.
- Favorite-состояние одинаково на карточке товара, детальной странице и `/favorites`.
- Header не превращается в большую marketing-панель и не отнимает первый экран.

## Этап 4. Надёжные изображения

### Задача

Текущий `getProductImageSrc` проверяет строку URL заранее, но не умеет обработать сетевую ошибку во время загрузки. Нужен общий client component для изображения товара.

Предпочтительное место:

```txt
src/entities/product/ui/ProductImage.tsx
```

### Поведение

- Сначала отображается основной `src`.
- При `onError` компонент один раз переключается на локальный fallback.
- Ошибка fallback не запускает бесконечный цикл.
- У карточки и страницы товара одинаковая логика.
- Сохраняется фиксированный aspect ratio, чтобы сетка не прыгала.

### Fallback

Подготовить одну локальную заглушку в стиле AI Slop Shop:

```txt
public/images/product-fallback.webp
```

Она должна выглядеть как намеренная часть бренда, а не как сломанная картинка браузера.

### Зачёт

- Намеренно битый URL заменяется fallback.
- Нет повторного `onError`-цикла.
- Card и Details не меняют размеры при ошибке.
- Alt остаётся названием товара.

### Доставка и кеширование изображений

Изначально `ProductCard` и `ProductDetails` использовали `next/image` с `unoptimized`, поэтому браузер получал исходные JPEG напрямую из InsForge Storage. `unoptimized` удалён: теперь Next.js может создавать варианты подходящего размера, менять формат и кешировать их через `/_next/image`.

`next/image` уже использует `loading="lazy"` по умолчанию. Поэтому нижние карточки начинают загружаться только при приближении к viewport; вручную добавлять lazy loading ко всем изображениям не нужно.

### Результат локального эксперимента — завершён

- InsForge Storage отдаёт `ETag`, `Last-Modified` и закешированный CloudFront-ответ, но без явного `Cache-Control` для браузера.
- При `unoptimized` повторная загрузка могла передавать полный JPEG размером около 100-250 KB.
- `unoptimized` удалён в `ProductCard` и `ProductDetails`.
- Lazy loading нижних карточек продолжает работать.
- Повторные локальные запросы к оптимизированным изображениям передают около `0.2 kB` служебных данных вместо полного JPEG.
- Следующая контрольная точка — повторить измерение после deployment на Vercel.

- [x] В DevTools Network проверить прямой InsForge URL, `ETag`, размер ответа и повторную загрузку.
- [x] Удалить `unoptimized` из `ProductCard` и `ProductDetails`.
- [x] Сохранить точный InsForge `remotePatterns`, не разрешая произвольные внешние домены.
- [x] Подтвердить локально lazy loading и кеширование через `/_next/image`.
- [ ] Проверить переходы `catalog -> product -> cart -> catalog` без отключённого browser cache.
- [ ] Убедиться, что `sizes` создаёт подходящий `srcset`: мобильная карточка не получает desktop-вариант.
- [ ] Проверить формат и полный размер первого ответа оптимизатора при отключённом кеше.
- [ ] После deployment повторить измерение на Vercel и сравнить transferred bytes и LCP.
- [ ] Возвращать `unoptimized` или менять image delivery только при воспроизводимой ошибке оптимизатора.

### Первый экран и LCP

- Не ставить `loading="eager"` или `preload` на все карточки: это отменит пользу lazy loading и создаст конкуренцию запросов.
- Повышать приоритет только для одного подтверждённого LCP-изображения после измерения Lighthouse/DevTools.
- Для детальной страницы главным LCP-кандидатом является крупное изображение товара; для каталога кандидат зависит от viewport, поэтому нельзя без измерений preload-ить весь первый ряд.

### Skeleton и blur

Белый фон до загрузки сейчас выглядит как пустая карточка. Нужен визуальный loading state внутри стабильного квадратного контейнера.

Первый вариант:

- спокойный skeleton без изменения размеров;
- после `onLoad` изображение плавно появляется;
- анимация отключается при `prefers-reduced-motion`.

Настоящий `placeholder="blur"` для remote URL требует ручной `blurDataURL`. Не создавать отдельный сетевой запрос за thumbnail для каждой карточки. Если нужен индивидуальный blur, генерировать крошечный data URL во время подготовки/seed товара и хранить его рядом с metadata. До этого общий skeleton проще и дешевле.

### Кеш Next.js

- Сначала использовать стандартный cache TTL оптимизатора и проверить фактические заголовки.
- Не увеличивать `minimumCacheTTL` вслепую: у Next.js нет удобной точечной инвалидации уже закешированного изображения.
- При замене изображения предпочесть новый `image_key` или версионированный URL, чтобы старый кеш не маскировал обновление.

### Зачёт кеширования

- повторный переход не скачивает без причины полный исходный JPEG;
- карточка получает изображение подходящего размера, а не desktop-оригинал на мобильном;
- изображения не обрезаются и не вызывают layout shift;
- кеш не мешает обновлению файла после осознанной замены изображения.

## Отдельная текущая задача: упростить favorites

Сейчас `useFavorites` искусственно имитирует серверную операцию через `useOptimistic`, `startTransition` и задержку `500 ms`. Реального запроса нет, поэтому optimistic state создаёт лишнее мигание на мобильном устройстве.

Решение для текущей версии без Authentication:

- оставить `favoritesStore`, `useSyncExternalStore` и `localStorage`;
- удалить `useOptimistic`, `startTransition` и искусственный `setTimeout`;
- вызывать `favoritesStore.toggleFavorite(id)` сразу;
- сохранить cross-tab синхронизацию через событие `storage`;
- не создавать таблицу server favorites и не выполнять дополнительные запросы InsForge.

### Зачёт favorites

- сердце переключается сразу и не мигает на телефоне;
- после reload состояние сохраняется;
- вторая вкладка получает изменение;
- один клик приводит ровно к одному переключению;
- в Network нет запросов favorites.

## Позже: infinite scroll

Для текущих 47 товаров infinite scroll не является срочной задачей: `next/image` уже лениво загружает нижние изображения при приближении к viewport, а один запрос каталога остаётся достаточно небольшим.

Вернуться к настоящему infinite scroll, когда каталог заметно вырастет. Тогда:

- InsForge-запрос получает товары порциями через `range` или эквивалентную пагинацию SDK;
- `IntersectionObserver` следит за нижним sentinel;
- следующая порция добавляется к уже показанным товарам;
- состояния `isLoadingMore`, `hasMore` и retry отображаются явно;
- фильтры и сортировка сбрасывают список на первую порцию;
- остаётся доступная кнопка `Load more` как fallback.

Простое скрытие части уже загруженного массива не считается infinite scroll, потому что не уменьшает исходный сетевой запрос.

## Этап 8. Архитектура Public API

Выполнять после основных пользовательских функций и стабилизации структуры проекта. Не начинать с массового механического рефакторинга всего репозитория.

### Цель

Каждый самостоятельный модуль предоставляет наружу только поддерживаемый публичный интерфейс через `index.ts`. Внешний код не должен зависеть от внутреннего расположения файлов конкретной feature или entity.

Пример:

```txt
src/features/cart/
  index.ts
  model/
  ui/
```

```ts
// src/features/cart/index.ts
export { useCartContext } from "./model/CartContext";
export { AddToCartControls } from "./ui/AddToCartControls";
```

Потребитель импортирует из публичного API:

```ts
import { AddToCartControls } from "@/features/cart";
```

а не обращается к внутреннему файлу напрямую:

```ts
import { AddToCartControls } from "@/features/cart/ui/AddToCartControls";
```

### Правила внедрения

- Добавлять `index.ts` на границе самостоятельных `features`, `entities` и подходящих сегментов `shared`.
- Экспортировать только то, что действительно используется снаружи; внутренние helpers и детали модели не раскрывать автоматически.
- Внутри одного модуля сохранять прямые относительные импорты, чтобы его файлы не импортировали сами себя через собственный barrel.
- Не создавать один глобальный `index.ts`, который реэкспортирует весь проект.
- Следить за циклическими зависимостями между `entities`, `features` и `app`.
- Проводить миграцию небольшими вертикальными срезами: сначала один модуль, затем проверка lint, TypeScript и build.

### Порядок

1. Зафиксировать границы текущих модулей и их реальные внешние потребители.
2. Начать с `entities/product`, `features/cart` и `features/favorites`.
3. Добавить минимальные Public API и перевести внешние импорты.
4. Затем обработать каталог и переиспользуемые части `shared`.
5. Удалять deep imports только после появления эквивалентного публичного экспорта.

### Зачёт

- Внешние потребители импортируют модуль через его Public API.
- Внутренние файлы не экспортируются без необходимости.
- Нет циклических зависимостей и self-import через `index.ts`.
- После каждого среза проходят lint, TypeScript и production build.
