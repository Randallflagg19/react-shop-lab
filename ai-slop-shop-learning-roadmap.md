# AI Slop Shop — Product Engineering Learning Roadmap

Статус: **новый активный учебный roadmap**.

Цель: продолжать развивать настоящий магазин и снова писать код самостоятельно. Каждый этап должен одновременно:

- решать заметную пользовательскую проблему;
- давать практику React, TypeScript или Next.js;
- оставлять проверяемый результат для портфолио;
- не добавлять фальшивую функцию без данных, backend или понятного сценария.

Этот roadmap продолжает завершённый `react-shop-lab-roadmap-utf8-bom.md` и забирает полезные незакрытые задачи из `ai-slope-shop-frontend-roadmap.md`.

## Текущая точка проекта

Уже готово:

- каталог из InsForge с 47 товарами;
- поиск, категории и сортировка;
- детальная страница товара;
- cart и favorites с `localStorage` и синхронизацией вкладок;
- quantity через `useReducer` и Context;
- общий header, страницы `/cart` и `/favorites`;
- адаптивный визуальный стиль AI Slop Shop;
- FSD-рефакторинг базовых границ;
- безопасный read-only anon-доступ к `products` и `categories`;
- production deployment.

Главные реальные пробелы:

- сетевые ошибки и битые изображения восстанавливаются не везде;
- состояние каталога нельзя сохранить ссылкой или кнопкой Back;
- пользовательские действия дают мало обратной связи;
- нет automated tests;
- нет route-level loading/error UX и динамических metadata товара;
- frontend-модули пока импортируются через внутренние пути;
- нет измеряемых performance-результатов и CI-проверки.

## Как проходить этапы

На каждом этапе:

1. Сначала своими словами описать состояние, события и ожидаемое поведение.
2. Написать типы и основной алгоритм без копирования готового решения.
3. Проверить happy path, ошибку, пустое состояние и граничный случай.
4. Только после этого просить review или подсказку.
5. Исправить замечания самостоятельно.
6. Добавить тест или короткое доказательство результата.
7. Зафиксировать в README, чему научился и почему выбрал эту архитектуру.

Правило помощи агента: по умолчанию агент объясняет, задаёт вопросы и делает review. Редактировать реализацию за тебя — только по прямой просьбе.

## Этап 1. Единый надёжный ProductImage

### Пользовательская ценность

Карточка, страница товара и корзина не показывают broken image и не прыгают при загрузке.

### Что написать самому

- `ProductImage` с единым API;
- состояния `loading`, `loaded`, `fallback`;
- однократное переключение на локальный fallback через `onError`;
- skeleton и плавное появление без layout shift;
- варианты `contain` и `cover` для разных мест интерфейса.

### Практика

`useState`, события изображения, discriminated union, controlled rendering, client boundary.

### Зачёт

- намеренно битый URL показывает брендированный fallback;
- ошибка fallback не создаёт цикл;
- Card, Details и Cart используют один компонент;
- `prefers-reduced-motion` учитывается.

### Для портфолио

Тест `onError -> fallback` и короткое сравнение layout shift до/после.

## Этап 2. Состояние запроса как конечный автомат и Retry

### Пользовательская ценность

При временной ошибке InsForge пользователь понимает, что произошло, и может повторить загрузку без перезагрузки страницы.

### Что написать самому

- заменить разрозненные `isLoading/error/products` на типизированное состояние `idle | loading | success | error`;
- действия reducer для начала, успеха, ошибки и retry;
- сохранить `AbortController` и защиту от устаревшего ответа;
- добавить кнопку «Повторить»;
- не стирать уже показанные товары при фоновом повторе запроса.

### Практика

`useReducer`, `useEffect`, `useCallback`, race conditions, cleanup, TypeScript narrowing.

### Зачёт

Retry работает после искусственно вызванной ошибки, двойной запрос не перетирает более свежий результат.

## Этап 3. Каталог, состояние которого живёт в URL

### Пользовательская ценность

Отфильтрованный каталог можно добавить в закладки, отправить другому человеку и восстановить кнопкой Back.

Пример:

```txt
/?q=плащ&category=clothing&sort=price-desc
```

### Что написать самому

- parser и serializer параметров;
- валидацию неизвестных `category` и `sort`;
- синхронизацию search/category/sort с URL;
- сброс отдельного фильтра и всех фильтров;
- сохранить отзывчивый controlled input и debounce.

### Практика

`useSearchParams`, `useRouter`, `useTransition`, `URLSearchParams`, derived state, `Suspense` boundary согласно Next.js 16.

### Зачёт

Reload, Back/Forward и скопированная ссылка восстанавливают одинаковый каталог без циклических обновлений.

---

## Этап 4. Система уведомлений без библиотеки

### Пользовательская ценность

Добавление в корзину, удаление и ошибки получают короткую понятную обратную связь.

### Что написать самому

- `ToastProvider` и `useToast`;
- reducer с очередью уведомлений;
- автоматическое закрытие;
- ручное закрытие;
- ограничение количества видимых сообщений;
- live region для screen reader;
- корректный cleanup таймеров.

### Практика

`useReducer`, Context, `useRef`, `useEffect`, идентификаторы, cleanup, accessibility.

### Зачёт

Несколько быстрых действий не теряют сообщения, таймеры не обновляют размонтированный UI.

---

## Этап 5. Undo для удаления из корзины

### Пользовательская ценность

Случайно удалённый товар можно вернуть одним действием.

### Что написать самому

- action, который хранит удалённый `CartItem` и его позицию;
- toast «Товар удалён — Вернуть»;
- восстановление количества и порядка;
- отдельное подтверждение перед полной очисткой корзины;
- полезное empty state с переходом в каталог.

### Практика

Reducer design, immutable update, временное состояние, callback actions, edge cases.

### Зачёт

Undo возвращает точный товар и quantity; повторное удаление и Clear не создают рассинхронизацию persistence.

---

## Этап 6. Недавно просмотренные товары

### Пользовательская ценность

После переходов по каталогу пользователь может быстро вернуться к последним товарам.

### Что написать самому

- persistent store последних 6 уникальных ID;
- добавление при открытии product page;
- перемещение повторно открытого товара в начало;
- удаление устаревших ID, которых больше нет в каталоге;
- блок «Недавно смотрели» без текущего товара.

### Практика

Повторное осмысленное применение `useSyncExternalStore`, immutable snapshot, `localStorage`, cross-tab event.

### Зачёт

Порядок стабилен после reload и между вкладками; дубликатов нет.

## Этап 7. Похожие товары без нового backend

### Пользовательская ценность

На детальной странице появляются релевантные альтернативы из той же категории.

### Что написать самому

- чистую функцию ранжирования;
- исключение текущего товара;
- ограничение результата;
- предсказуемый fallback, если категория маленькая;
- переиспользование ProductCard без знания о странице товара.

### Практика

Чистые функции, `useMemo` только при реальной необходимости, deterministic sorting, композиция Server/Client Components.

### Зачёт

Алгоритм покрыт unit-тестами, результат не меняет исходный массив.

## Этап 8. Accessibility-проход как отдельная инженерная задача

### Пользовательская ценность

Магазин полностью управляется клавиатурой и понятно озвучивается screen reader.

### Что проверить и исправить

- landmarks и иерархию заголовков;
- skip link;
- видимый focus;
- доступные имена icon buttons;
- сообщение об изменении количества и итоговой цены;
- focus после удаления строки корзины;
- contrast и `prefers-reduced-motion`;
- отсутствие ловушек focus.

### Практика

`useId`, `useRef`, semantic HTML, ARIA live regions, focus management.

### Зачёт

Основные сценарии выполняются без мыши; Lighthouse accessibility и ручной checklist сохранены в README.

## Этап 9. Unit-тесты модели

### Пользовательская ценность

Изменения корзины, фильтров и persistence перестают ломать старые сценарии незаметно.

### Что написать самому

Настроить Vitest и протестировать:

- cart reducer;
- pluralize и `formatPrice`;
- URL parser/serializer;
- related-products ranking;
- favorites/recently-viewed snapshots;
- обработку повреждённого JSON из `localStorage`.

### Практика

Test design, fixtures/builders, pure functions, boundary cases, Arrange–Act–Assert.

### Зачёт

Тесты проверяют поведение, а не внутреннюю реализацию; есть отдельная команда `npm test`.

## Этап 10. Component integration tests

### Пользовательская ценность

Проверяются настоящие действия пользователя, а не только функции.

### Что написать самому

С React Testing Library проверить:

- retry каталога;
- добавление выбранного quantity;
- уменьшение количества и удаление с `1`;
- undo удаления;
- переключение favorites;
- image fallback;
- доступные имена и disabled states.

### Практика

RTL queries, `user-event`, async assertions, mock boundaries, testing accessibility contracts.

### Зачёт

Нет тестов, которые ищут элементы по CSS-классам или повторяют реализацию компонента.

## Этап 11. E2E критического пути

### Пользовательская ценность

Перед релизом автоматически проверяется, что магазин работает как единое приложение.

### Сценарии Playwright

1. Открыть каталог и найти товар.
2. Применить категорию и сортировку, проверить URL.
3. Открыть товар.
4. Выбрать quantity и добавить в корзину.
5. Изменить quantity в корзине.
6. Перезагрузить страницу и проверить persistence.
7. Добавить/удалить favorite.
8. Проверить mobile viewport.

### Практика

E2E boundaries, устойчивые locators, test isolation, browser storage, responsive testing.

### Зачёт

Тесты проходят локально на чистом storage и не зависят от порядка запуска.

---

## Этап 12. Полные состояния App Router и metadata

### Пользовательская ценность

Навигация показывает route-level loading, неожиданные ошибки имеют recovery UI, а вкладка и превью конкретного товара содержат его название.

### Что написать самому

- нужные `loading.tsx`, `error.tsx`, `not-found.tsx` без дублирования локальных состояний запроса;
- `generateMetadata` для product route;
- корректный `metadataBase` после фиксации production URL;
- понятную кнопку recovery в error boundary;
- логирование ошибки без показа технических деталей пользователю.

### Практика

Server/Client boundaries, Next.js file conventions, error boundaries, `reset()`, dynamic metadata.

### Зачёт

Проверены slow navigation, неизвестный slug и искусственно вызванная route error.

## Этап 13. Настоящий optimistic UI — только после Authentication

Статус: **advanced, выполнять только если нужен пользовательский аккаунт**.

### Пользовательская ценность

Favorites принадлежат пользователю и доступны на разных устройствах, а не только в одном браузере.

### Последовательность

1. Подключить InsForge Authentication.
2. Спроектировать таблицу user favorites с foreign keys и RLS.
3. Написать repository/API функции.
4. Перенести favorites с local-only store на server state.
5. Только теперь применить `useOptimistic` с настоящим rollback.
6. Продумать миграцию локальных favorites после первого входа.

### Практика

Auth state, real async mutation, `useOptimistic`, rollback, RLS, optimistic concurrency, merge strategy.

### Зачёт

Два разных пользователя не видят favorites друг друга; ошибка сети откатывает optimistic update.

## Этап 14. Public API модулей

### Пользовательская ценность

Новые функции можно добавлять без массовой правки deep imports и случайного доступа к внутренностям feature.

### Что написать самому

- определить внешний контракт `entities/product`, `features/cart`, `features/favorites`;
- добавить минимальные `index.ts`;
- перевести только внешних потребителей;
- не делать self-import через barrel;
- проверить циклические зависимости;
- затем обработать catalog и shared.

### Практика

FSD boundaries, dependency direction, API design, TypeScript exports.

### Зачёт

Внешний код не импортирует `model/*` и `ui/*` напрямую без осознанной причины; build проходит после каждого среза.

## Этап 15. Измеряемая производительность

### Пользовательская ценность

Магазин не только выглядит быстрым, но имеет измеримые показатели.

### Что написать самому

- узкий client component с `useReportWebVitals`;
- стабильный callback без повторной отправки метрик;
- dev-лог или выбранный analytics endpoint;
- замеры LCP, CLS и INP на catalog/product/cart;
- исправление одной подтверждённой проблемы;
- документ «до/после», а не набор случайных `memo`.

### Практика

Stable references, Core Web Vitals, profiling, evidence-driven optimization.

### Зачёт

В README есть измерения, устройство/viewport, найденная причина и эффект исправления.

## Этап 16. CI и портфолио-доказательства

### Пользовательская ценность

Каждое изменение автоматически проверяется, а работодатель видит инженерный процесс.

### Что сделать

- CI: lint, TypeScript, unit tests, production build;
- отдельный E2E job или документированная причина его запуска вручную;
- обновить README: live URL, screenshots, architecture, тестовая стратегия;
- добавить таблицу решений: проблема → варианты → выбор → trade-off;
- описать три сложных бага и способ диагностики;
- записать короткий demo flow проекта.

### Практика

CI, release discipline, technical writing, communication of engineering decisions.

### Зачёт

Новый pull request нельзя слить при провале обязательной проверки; README объясняет не только что сделано, но и почему.

## Что сознательно не добавлять сейчас

- infinite scroll для 47 товаров;
- фиктивный checkout без orders/payment backend;
- отзывы без пользователей, moderation и реальной модели данных;
- промокоды без pricing rules;
- сравнение товаров, пока у них нет сравнимых характеристик;
- Redux/React Query только ради строки в резюме;
- `useMemo`, `useCallback`, `memo` без измеренной причины;
- Server Actions только ради знакомства с названием API;
- новый визуальный redesign до закрытия reliability и tests.

## Итоговый Definition of Done

Новый учебный roadmap завершён, когда:

- ошибки сети и изображений имеют recovery;
- состояние каталога воспроизводится по URL;
- cart actions дают feedback и поддерживают undo;
- ключевые функции покрыты unit/component/E2E тестами;
- приложение доступно с клавиатуры;
- route states и metadata закончены;
- внешние импорты проходят через понятные Public API;
- производительность измерена, а не угадана;
- CI защищает main branch;
- README показывает решения, trade-offs и доказательства качества;
- ты можешь без подсказки объяснить состояние, события и границы каждого нового модуля.
