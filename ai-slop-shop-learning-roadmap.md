# AI Slop Shop — Product Engineering Learning Roadmap

Статус: **активный учебный roadmap**. Этапы 1–5 завершены, следующий фокус — Этап 8, accessibility-проход. Этапы 6–7 остаются опциональными продуктовыми улучшениями после стабилизации базового UX.

Цель: продолжать развивать настоящий магазин и снова писать код самостоятельно. Каждый этап должен одновременно:

- решать заметную пользовательскую проблему;
- давать практику React, TypeScript или Next.js;
- оставлять проверяемый результат для портфолио;
- не добавлять фальшивую функцию без данных, backend или понятного сценария.

Этот roadmap продолжает завершённый `oldRoadmaps/react-shop-lab-roadmap-utf8-bom.md` и забирает полезные незакрытые задачи из `oldRoadmaps/ai-slope-shop-frontend-roadmap.md`.

## Текущая точка проекта

Уже готово:

- каталог из InsForge с 55 товарами через server-only Next.js API;
- поиск, категории и сортировка;
- детальная страница товара;
- cart и favorites с `localStorage` и синхронизацией вкладок;
- quantity через `useReducer` и Context;
- общий header, страницы `/cart` и `/favorites`;
- адаптивный визуальный стиль AI Slop Shop;
- FSD-рефакторинг базовых границ;
- безопасный read-only anon-доступ к `products` и `categories`;
- локальные product images и единый fallback-компонент;
- конечный автомат загрузки каталога с Retry и защитой от устаревших запросов;
- URL как источник состояния поиска, категории и сортировки каталога;
- фильтры каталога обновляются через native History API и отбрасывают посторонние query-параметры;
- кастомная система toast-уведомлений без UI-библиотеки;
- toast-уведомления для добавления в корзину и действий избранного;
- адаптированное мобильное расположение toast-уведомлений;
- защита мобильного поиска от iOS auto-zoom при фокусе;
- 11 тестов mapper, client transport, Route Handler и ProductImage;
- production deployment.

Главные реальные пробелы:

- критические границы уже имеют 11 тестов, но cart/favorites/filtering почти не покрыты;
- доступность уже частично учтена точечно, но нет системного keyboard/screen reader прохода;
- нет route-level loading/error UX и динамических metadata товара;
- frontend-модули пока импортируются через внутренние пути;
- нет измеряемых performance-результатов и CI-проверки.

## Как проходить этапы

На каждом этапе:

1. Сначала своими словами описать состояние, события и ожидаемое поведение.
2. Написать типы и основной алгоритм без копирования готового решения.
3. Проверить happy path, ошибку, пустое состояние и граничный случай.
4. Только после этого просить review или подсказку.
5. Исправить замечания самостоятельно.
6. Добавить тест или короткое доказательство результата.
7. Зафиксировать в README, чему научился и почему выбрал эту архитектуру.

Правило помощи агента: по умолчанию агент объясняет, задаёт вопросы и делает review. Редактировать реализацию за тебя — только по прямой просьбе.

## Этап 1. Единый надёжный ProductImage

Статус: **выполнено**.

### Пользовательская ценность

Карточка, страница товара и корзина не показывают broken image и не прыгают при загрузке.

### Что реализовано

- `ProductImage` с единым API;
- однократное переключение на локальный fallback через `onError`;
- защита от цикла при ошибке самого fallback;
- использование в Card, Details и Cart;
- стабильные контейнеры изображения без дополнительного layout shift;
- три component-теста исходного изображения и fallback-поведения.

### Практика

`useState`, события изображения, derived state, client boundary, React Testing Library.

### Зачёт

- намеренно битый URL показывает брендированный fallback — выполнено;
- ошибка fallback не создаёт цикл — выполнено;
- Card, Details и Cart используют один компонент — выполнено;
- тесты проходят — выполнено.

Skeleton, отдельные `loading/loaded` состояния и fade-анимация сознательно не добавлены: фиксированные контейнеры уже удерживают layout, а самостоятельной пользовательской проблемы для дополнительной анимации не обнаружено. Если позже появится fade, тогда потребуется `prefers-reduced-motion`.

### Для портфолио

Тесты `onError -> fallback` и `fallback error -> без цикла`.

## Этап 2. Состояние запроса как конечный автомат и Retry

Статус: **выполнено**.

### Пользовательская ценность

При временной ошибке VPS/Vercel → InsForge пользователь понимает, что произошло, и может повторить загрузку без перезагрузки страницы. Этот этап не лечит недоступность всего сайта или мобильной сети: Retry возможен только после загрузки приложения.

### Что реализовано

- разрозненные `isLoading/error/products` заменены типизированным состоянием `idle | loading | success | error`;
- действия reducer описывают начало, успех и ошибку запроса;
- `AbortController` хранится в `useRef`, предыдущий запрос отменяется перед новым;
- проверка сигнала и принадлежности контроллера защищает от устаревшего ответа и неверного cleanup;
- стабильный `loadProducts` через `useCallback` возвращается как `retry`;
- общий `ProductsLoadError` с кнопкой «Повторить» используется в каталоге и избранном;
- уже показанные товары сохраняются при повторной загрузке и временной ошибке;
- обработанная клиентская ошибка не дублируется через `console.error` в Next.js overlay.

### Практика

`useReducer`, `useEffect`, `useCallback`, race conditions, cleanup, TypeScript narrowing.

### Зачёт

- запрос `/api/products` намеренно блокировался в DevTools — выполнено;
- после снятия блокировки Retry загружает товары без перезагрузки страницы — выполнено;
- повторный запрос отменяет предыдущий и не принимает его устаревший результат — выполнено;
- ESLint и 11 существующих тестов проходят — выполнено.

## Этап 3. Каталог, состояние которого живёт в URL

Статус: **выполнено**.

### Пользовательская ценность

Отфильтрованный каталог можно добавить в закладки, отправить другому человеку и восстановить кнопкой Back.

Пример:

```txt
/?q=плащ&category=clothing&sort=price-desc
```

### Что реализовано

- типизированные `CatalogFilters`, `CatalogCategory` и существующий `SortBy` задают допустимое состояние;
- чистый parser превращает read-only search params во внутренние фильтры;
- serializer создаёт компактный `URLSearchParams` и не записывает значения `all/default`;
- неизвестные `category` и `sort` безопасно сводятся к значениям по умолчанию;
- URL стал единым источником истины для search/category/sort без дублирующих `useState`;
- категория и сортировка используют `window.history.pushState`, сохраняют историю и нормализуют URL;
- поиск использует `history.replaceState`, поэтому ввод не создаёт запись истории на каждую букву;
- посторонние query-параметры вроде `v`, `utm_*` и случайного мусора удаляются при следующем изменении фильтра;
- controlled input обновляется сразу, а фильтрация товаров сохраняет существующий debounce;
- отдельные фильтры сбрасываются стандартными контролами, полный сброс выполняется переходом по логотипу на `/`;
- `Catalog` обёрнут в `Suspense` для статического prerendering с `useSearchParams` в Next.js 16;
- неиспользуемый Oswald удалён вместе с лишним preload и сетевой зависимостью сборки.
- эксперимент с `useOptimistic` для фильтров удалён: для URL-only состояния он создавал вторую временную правду и мог откатываться к старому URL.

### Практика

`useSearchParams`, native History API, `URLSearchParams`, derived state, `Suspense` boundary согласно Next.js 16.

### Зачёт

- Reload сохраняет поиск, категорию и сортировку — выполнено;
- Back/Forward восстанавливают состояние каталога — выполнено;
- скопированная ссылка открывает такую же выдачу — выполнено;
- некорректные значения URL не ломают каталог — выполнено;
- production build со статическим маршрутом `/` проходит — выполнено.

## Этап 4. Система уведомлений без библиотеки

Статус: **выполнено**.

### Пользовательская ценность

Добавление в корзину на product page, удаление и ошибки получают короткую понятную обратную связь. Изменения `+ / −` внутри самой корзины не создают toast: результат там уже виден непосредственно в строке товара и итоговой сумме.

### Что реализовано

- `ToastProvider` и `useToast` без сторонней UI-библиотеки;
- reducer с ограниченной очередью уведомлений;
- автоматическое закрытие уведомлений с cleanup таймеров;
- ручное закрытие через кнопку;
- `aria-live="polite"` для screen reader;
- варианты `success`, `info` и `error`;
- cart toast при добавлении товара на product page;
- favorite toast при добавлении и удалении из избранного;
- разные визуальные варианты для корзины, избранного и ошибки;
- стек из двух уведомлений с новым toast поверх предыдущего;
- адаптивное мобильное расположение toast-уведомлений над CTA-зоной товара;
- мобильный search input защищён от iOS auto-zoom через `font-size: 16px`.

### Архитектурные решения

- `+ / −` в корзине не показывают toast, потому что результат виден прямо в строке товара;
- максимум видимых уведомлений ограничен двумя: этого достаточно для понятного feedback и не перегружает мобильный экран;
- одинаковые быстрые действия пока создают новый toast поверх старого, без отдельной логики merge/count;
- действие «Перейти в корзину» сознательно не добавлено: текущий toast короткий и не перетягивает на себя навигацию;
- error-вариант стилизован, но пока используется как резерв для будущих сценариев.

### Практика

`useReducer`, Context, `useRef`, `useEffect`, идентификаторы, cleanup, accessibility.

### Зачёт

- добавление с product page заметно без наблюдения за badge в header — выполнено;
- добавление/удаление избранного даёт локальную обратную связь — выполнено;
- таймеры не обновляют размонтированный UI — выполнено;
- mobile toast не перекрывает полностью CTA-кнопки — выполнено;
- desktop toast остался в правой верхней зоне — выполнено;
- ESLint проходит — выполнено.

## Этап 5. Undo для удаления из корзины

Статус: **выполнено**.

### Пользовательская ценность

Случайно удалённый товар можно вернуть одним действием.

### Что реализовано

- action, который хранит удалённый `CartItem` и его позицию;
- toast «Товар удалён из корзины» с действием «Вернуть»;
- восстановление количества и порядка;
- отдельное inline-подтверждение перед полной очисткой корзины без layout jump;
- полезное empty state с кнопкой «Перейти к покупкам».

### Выбранный UX-сценарий

- при удалении одной строки товар исчезает из корзины сразу;
- появляется один компактный toast в зоне между золотыми разделителями;
- toast живёт столько же, сколько остальные уведомления;
- действие «Вернуть» восстанавливает товар с прежним quantity;
- если toast закрылся или истёк, undo больше недоступен;
- «Очистить корзину» первым кликом не очищает корзину, а раскрывает inline-confirm внутри summary;
- confirm заранее занимает стабильную зону, чтобы summary не дёргался;
- `window.confirm()` и modal-dialog на этом этапе не используются.

### Практика

Reducer design, immutable update, временное состояние, callback actions, edge cases.

### Зачёт

- Undo возвращает точный товар и quantity — выполнено;
- удаление строки сразу даёт понятный toast с действием «Вернуть» — выполнено;
- повторное удаление не создаёт дубликаты при восстановлении — выполнено;
- Clear требует inline-подтверждение и не использует `window.confirm()` — выполнено;
- empty state корзины ведёт обратно в каталог — выполнено;
- toast на product page, catalog, cart и favorites имеет контекстно удобную мобильную позицию — выполнено;
- ESLint проходит — выполнено.

## Этап 8. Accessibility-проход как отдельная инженерная задача

Статус: **следующий активный этап**.

### Пользовательская ценность

Магазином можно пользоваться без мыши: через клавиатуру, screen reader, увеличение масштаба и сниженное движение. Доступность не должна ломать dark fantasy стиль, но фокус, названия кнопок и динамические изменения должны быть понятны не только визуально.

### Принцип этапа

Сначала правильная семантика и клавиатура, потом screen reader, и только после этого дополнительные ARIA-атрибуты. Не добавлять `role` или `aria-*` ради галочки, если нативный HTML уже решает задачу.

### Что уже есть

- `aria-live="polite"` в toast viewport;
- `aria-pressed` у category chips;
- `label` для search input и sort select;
- semantic `button` для интерактивных действий;
- empty states корзины и избранного с понятными переходами;
- iOS search input auto-zoom исправлен через `font-size: 16px`.

### Что не делать на старте

- не превращать категории в ARIA tabs: это фильтры, им достаточно button + `aria-pressed`;
- не ставить `role="alert"` на обычные toast-уведомления;
- не озвучивать live-region на каждую букву поиска;
- не делать один большой diff “accessibility всего магазина”;
- не переписывать визуальный дизайн до ручного аудита.

### Срез 8.1. Ручной keyboard audit

Пройти без мыши:

- catalog: поиск, категории, сортировка, карточки, favorite buttons;
- product page: добавление в корзину, quantity, favorite action;
- cart: quantity, remove, undo, clear confirmation;
- favorites: карточки и удаление из избранного;
- toast: close и action-кнопка.

Записывать проблемы в формате:

```txt
страница -> элемент -> проблема -> ожидаемое поведение
```

### Срез 8.2. Первый вертикальный flow: favorites

Починить один законченный сценарий:

```txt
catalog -> добавить товар в избранное -> услышать/увидеть toast -> открыть favorites -> удалить товар из избранного
```

Что проверить и при необходимости исправить:

- заметный `focus-visible` для ссылок, кнопок, input и select в arcane theme;
- favorite button имеет уникальное доступное имя с названием товара;
- `Heart` icon остаётся `aria-hidden`;
- `aria-pressed` корректно отражает состояние favorite;
- одинаковые ссылки «Осмотреть артефакт» получают скрытый контекст с названием товара;
- toast остаётся polite live-region и имеет доступные close/action кнопки.

### Срез 8.3. Cart focus management

Починить поведение после удаления строки корзины:

- фокус не пропадает вместе с удалённой кнопкой;
- после удаления фокус попадает на логичный следующий элемент: соседняя строка, undo action или summary;
- undo доступен с клавиатуры;
- clear cart confirmation полностью управляется клавиатурой.

### Срез 8.4. Structure, motion, contrast

Проверить и исправить только подтверждённые проблемы:

- landmarks: `header`, `main`, структура страниц;
- порядок `h1/h2/h3`;
- skip link к основному содержимому;
- contrast важных текстов и кнопок;
- zoom 200%;
- `prefers-reduced-motion` для glow/transition/toast movement.

### Срез 8.5. Screen reader и доказательство

- пройти один сценарий VoiceOver на Mac;
- проверить, что нет «кнопка, кнопка» без имени;
- проверить, что текущая категория и favorite state понятны на слух;
- сохранить краткий accessibility checklist в README или roadmap;
- при желании приложить Lighthouse accessibility score как дополнительное, но не единственное доказательство.

### Практика

`useId`, `useRef`, semantic HTML, ARIA live regions, focus management.

### Зачёт

Основные сценарии выполняются без мыши; favorite flow и cart remove/undo понятны клавиатуре и screen reader; ручной checklist сохранён в README или roadmap. Lighthouse accessibility используется как дополнительная проверка, а не как замена ручному аудиту.

## Этап 10. Component integration tests

Статус: **частично начато**. ProductImage уже имеет три component-теста; пользовательские сценарии cart, retry, undo и favorites остаются.

### Пользовательская ценность

Проверяются настоящие действия пользователя, а не только функции.

### Что написать самому

С React Testing Library проверить:

- retry каталога;
- добавление выбранного quantity;
- уменьшение количества и удаление с `1`;
- undo удаления;
- переключение favorites;
- image fallback;
- доступные имена и disabled states.

### Практика

RTL queries, `user-event`, async assertions, mock boundaries, testing accessibility contracts.

### Зачёт

Нет тестов, которые ищут элементы по CSS-классам или повторяют реализацию компонента.

## Этап 11. E2E критического пути

### Пользовательская ценность

Перед релизом автоматически проверяется, что магазин работает как единое приложение.

### Сценарии Playwright

1. Открыть каталог и найти товар.
2. Применить категорию и сортировку, проверить URL.
3. Открыть товар.
4. Выбрать quantity и добавить в корзину.
5. Изменить quantity в корзине.
6. Перезагрузить страницу и проверить persistence.
7. Добавить/удалить favorite.
8. Проверить mobile viewport.

### Практика

E2E boundaries, устойчивые locators, test isolation, browser storage, responsive testing.

### Зачёт

Тесты проходят локально на чистом storage и не зависят от порядка запуска.

## Этап 12. Полные состояния App Router и metadata

### Пользовательская ценность

Навигация показывает route-level loading, неожиданные ошибки имеют recovery UI, а вкладка и превью конкретного товара содержат его название.

### Что написать самому

- нужные `loading.tsx`, `error.tsx`, `not-found.tsx` без дублирования локальных состояний запроса;
- `generateMetadata` для product route;
- корректный `metadataBase` после фиксации production URL;
- понятную кнопку recovery в error boundary;
- логирование ошибки без показа технических деталей пользователю.

### Практика

Server/Client boundaries, Next.js file conventions, error boundaries, `reset()`, dynamic metadata.

### Зачёт

Проверены slow navigation, неизвестный slug и искусственно вызванная route error.

## Этап 13. Настоящий optimistic UI — только после Authentication

Статус: **advanced, выполнять только если нужен пользовательский аккаунт**.

### Пользовательская ценность

Favorites принадлежат пользователю и доступны на разных устройствах, а не только в одном браузере.

### Последовательность

1. Подключить InsForge Authentication.
2. Спроектировать таблицу user favorites с foreign keys и RLS.
3. Написать repository/API функции.
4. Перенести favorites с local-only store на server state.
5. Только теперь применить `useOptimistic` с настоящим rollback.
6. Продумать миграцию локальных favorites после первого входа.

### Практика

Auth state, real async mutation, `useOptimistic`, rollback, RLS, optimistic concurrency, merge strategy.

### Зачёт

Два разных пользователя не видят favorites друг друга; ошибка сети откатывает optimistic update.

## Что сознательно не добавлять сейчас

- infinite scroll для 55 товаров;
