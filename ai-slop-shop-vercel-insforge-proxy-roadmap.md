# AI Slop Shop — Vercel → InsForge Proxy Learning Roadmap

Статус: **новый активный учебный roadmap**.

Цель: убрать прямое обращение браузера к InsForge, чтобы каталог работал без VPN, и на настоящей задаче изучить серверную часть Next.js 16.

Этот roadmap не переносит базу данных из InsForge. InsForge остаётся источником данных, Vercel исполняет Next.js, а 55 изображений товаров остаются статическими файлами проекта в `public/images/products`.

## Итоговая архитектура

```txt
Сейчас:
браузер ──X──> InsForge Database
          блокируется без VPN

После изменений:
браузер ──> GET /api/products на Vercel ──> InsForge Database
        └─> /images/products/*.jpg на Vercel
```

Vercel здесь — BFF (Backend for Frontend): небольшой серверный слой, предназначенный именно для frontend-приложения. Это не новая база данных и не копия InsForge.

## Зафиксированное решение по изображениям

55 изображений общим объёмом около 11 МБ остаются в `public/images/products` и отдаются через Vercel.

Это осознанное архитектурное решение:

- небольшой объём приемлем для deployment artifact;
- статические файлы доступны с того же домена и CDN Vercel;
- каталог не зависит от доступности InsForge Storage в браузере пользователя;
- возврат прямых Storage URL снова создал бы исходную проблему без VPN;
- проксирование каждого изображения через Route Handler добавило бы трафик, задержку и сложность без пользы для текущего масштаба.

В InsForge остаются PostgreSQL-таблицы `products` и `categories`, read-only политики/права и резервные файлы Storage. Приложение использует базу через сервер Vercel, но не использует InsForge Storage для показа изображений.

## Чему я научусь

- различать Client Component, Server Component и Route Handler;
- понимать, какой код исполняется в браузере, а какой на Vercel;
- проектировать простой HTTP API;
- разделять серверный доступ к данным и клиентский transport;
- работать с server-only environment variables;
- обрабатывать сетевые ошибки и HTTP-статусы;
- проверять архитектуру через Network и Vercel Logs;
- осознанно принимать решение о кэшировании.

## Правила прохождения

1. Сначала я сам описываю вход, выход и ошибки функции.
2. Затем пишу реализацию небольшими шагами.
3. Агент по умолчанию объясняет и делает review, а не пишет этап за меня.
4. После каждого этапа я проверяю результат руками.
5. В конце фиксирую в README проблему, решение и архитектурную схему.

## Этап 1. Зафиксировать исходную проблему — завершён

### Результат проверки 4 июля 2026 года

- Production: `https://react-shop-lab.vercel.app/`.
- Без VPN браузер напрямую вызывает `https://kmj65yri.eu-central.insforge.app/api/database/records/products?...`.
- Запрос инициирован клиентским JavaScript-чанком приложения на Vercel.
- Без VPN соединение остаётся в состоянии `Stalled` и завершается по тайм-ауту через `30.00 s`; HTTP-ответ от InsForge не получен.
- С VPN тот же `GET` завершается успешно: `304 Not Modified`, около `84.67 ms`. Код `304` означает, что сервер подтвердил актуальность уже закэшированного браузером ответа.
- Каталог и изображения после успешного получения данных отображаются.

### Вывод

Проблема воспроизведена и локализована. Это не ошибка SQL, RLS, mapper или файлов в `public`: без VPN недоступен прямой сетевой маршрут **из браузера пользователя** к домену InsForge. Следующий этап должен убрать этот клиентский маршрут и заменить его цепочкой Browser → Vercel Route Handler → InsForge.

### Сделать

- открыть production без VPN;
- в DevTools → Network найти прямой запрос к домену `*.insforge.app`;
- записать его URL, status/error и место вызова;
- повторить проверку с VPN;
- отдельно убедиться, что `/images/products/*.jpg` с Vercel открываются без VPN.

### Зачем

Мы отделяем две независимые вещи: изображения уже доступны с Vercel, а загрузку каталога блокирует прямой запрос браузера к InsForge.

### Зачёт

Выполнено. Есть описание и скриншоты воспроизводимой проблемы «до», которые нужно сравнить с Network-проверкой после этапа 6.

## Этап 2. Разобрать текущий путь данных — завершён

### Результат разбора

Текущий путь каталога:

```txt
Catalog / Favorites (Client Component)
  → useProducts()
  → fetchProducts(signal)
  → fetchInsforgeProducts(signal)
  → shared InsForge SDK client
  → HTTP-запрос из браузера к InsForge
  → ProductRow[]
  → mapProductRowToProduct()
  → Product[] с /images/products/{image_key}
```

Текущий путь детальной страницы:

```txt
ProductPage (Server Component на Vercel)
  → fetchProductBySlug(slug)
  → fetchInsforgeProductBySlug(slug)
  → HTTP-запрос с Vercel к InsForge
  → ProductRow | null
  → Product | notFound()
```

`useProducts.ts` сам не содержит директиву `"use client"`, потому что это не компонент-точка входа. Он попадает в клиентский граф модулей через импорт из `Catalog.tsx` и `favorites/page.tsx`, где директива уже установлена. Использование `useState` и `useEffect` означает, что этот hook можно вызывать только внутри клиентского React-компонента.

`insforgeProducts.ts` сейчас не имеет server-only границы. Одна его функция попадает в клиентский bundle через каталог, а другая исполняется на Vercel через серверную страницу товара. На следующем этапе эти ответственности нужно разделить.

Перенос изображений не исправил каталог: mapper получает `image_key` из строки базы. Пока запрос списка товаров не завершился, приложение не получает объекты `Product`, не строит карточки и не формирует их локальные `src`. Сами файлы в `public` при известном прямом URL доступны независимо от базы.

### Изучить

- `useProducts` запускает запрос из Client Component;
- клиентский `fetchProducts` сейчас вызывает InsForge SDK;
- `fetchInsforgeProducts` получает строки `products`;
- mapper превращает строку базы в доменный `Product` и выдаёт локальный путь изображения;
- страница товара уже является серверной и получает данные через Vercel.

### Написать самому

Короткую схему вызовов и ответить:

1. Где сейчас исполняется каждый файл?
2. Почему каталог ломается без VPN?
3. Почему перенос изображений не мог исправить запрос к базе?

### Зачёт

Выполнено. Путь клиентского каталога и server-to-server путь детальной страницы объяснены своими словами и сверены с кодом.

## Этап 3. Создать server-only клиент InsForge — завершён

### Результат

- Создан `src/shared/api/insforge.server.ts` с `import "server-only"`.
- Клиент использует серверные `INSFORGE_URL` и `INSFORGE_ANON_KEY`.
- Обе переменные добавлены локально и в Environment Variables проекта Vercel.
- Создан безопасный `.env.example` только с пустыми именами переменных.
- В `.gitignore` добавлено исключение `!.env.example`: пример попадёт в Git, а `.env.local` с реальными значениями останется проигнорированным.
- Используется read-only anon key; admin/API key не требуется.
- Старые `NEXT_PUBLIC_INSFORGE_*` временно сохранены до переключения каталога на `/api/products` в этапе 6.

### Сделать

- создать отдельный модуль InsForge для серверного кода;
- добавить в него `import "server-only"`, чтобы случайный импорт в Client Component завершался ошибкой сборки;
- читать `INSFORGE_URL` и `INSFORGE_ANON_KEY` без префикса `NEXT_PUBLIC_`;
- добавить названия переменных в `.env.example` без реальных значений;
- добавить эти переменные в Vercel Environment Variables;
- после проверки удалить зависимость frontend-кода от `NEXT_PUBLIC_INSFORGE_*`.

### Безопасность

- использовать **anon key**, а не admin/API key;
- сохранить уже проверенные права `SELECT` для `anon` и `authenticated`;
- не считать Route Handler заменой RLS и database grants;
- никогда не возвращать ключ в JSON-ответе и не логировать его.

### Зачёт

Выполнено для подготовительного server-only слоя. Полная production-проверка новых переменных состоится после подключения repository и Route Handler.

## Этап 4. Отделить repository от HTTP API — завершён

### Результат

- Создан server-only repository `src/entities/product/api/insforgeProducts.server.ts`.
- `fetchProductsFromInsforgeServer()` собирает запрос через InsForge SDK к таблице `products`.
- Query builder получает `select`, сортировку и ожидаемый тип до выполнения запроса через `await`.
- Ответ разбирается как `{ data, error }`; ошибка InsForge превращается в исключение.
- `ProductRow[]` преобразуется mapper-ом в доменный `Product[]` с локальными путями `/images/products/{image_key}`.
- Repository не знает об HTTP-ответах и UI, а его модуль нельзя импортировать в клиентский bundle.
- `npm run lint` проходит без ошибок.

Перенос server-side запроса отдельного товара по slug будет выполнен при проверке потребителей на этапе 7. Для Route Handler каталога repository уже готов.

### Сделать

Выделить серверную функцию, которая:

1. делает `select` из `products` через InsForge SDK;
2. проверяет `{ data, error }`;
3. преобразует `ProductRow[]` в `Product[]`;
4. возвращает доменные товары с путями `/images/products/...`;
5. выбрасывает понятную серверную ошибку при сбое InsForge.

### Зачем

Repository знает про InsForge и таблицу. Route Handler знает про HTTP. Компонент не должен знать ни о том, ни о другом.

### Зачёт

Выполнено на уровне server repository. Подключение функции как источника `/api/products` выполняется на следующем этапе.

## Этап 6. Переписать клиентский transport — завершён

### Результат

- `src/entities/product/api/products.ts` больше не реэкспортирует прямой InsForge-запрос.
- `fetchProducts(signal)` обращается к same-origin `/api/products`, проверяет `response.ok`, читает JSON и проверяет, что ответ является массивом.
- `useProducts` сохранил `AbortController`, cleanup и вызов `fetchProducts(controller.signal)`.
- Клиентская ветка не импортирует модули `*.server.ts`.
- В DevTools подтверждён `GET http://localhost:3000/api/products` со статусом `200 OK` и `Content-Type: application/json`.
- Каталог успешно получает товары и загружает изображения из `/images/products`.
- После production deploy приложение проверено без VPN на компьютере, по Wi-Fi на телефоне и через мобильный интернет: каталог, изображения, favorites и cart работают.
- `npm run lint` проходит без ошибок.

Красный запрос, оставшийся в Network рядом с успешным, относится к отдельной прерванной или неудачной попытке во время нестабильного локального соединения с InsForge. После очистки Network и повторной загрузки текущая цепочка отвечает успешно.

### Сделать

Клиентская `fetchProducts(signal)` должна:

- вызывать только `fetch("/api/products", { signal })`;
- проверять `response.ok` до чтения успешного ответа;
- преобразовывать ошибочный ответ в понятную ошибку приложения;
- вернуть тип `Promise<Product[]>`;
- больше не импортировать InsForge SDK или server-only repository.

### Сохранить

- `useEffect` в `useProducts`;
- `AbortController` и cleanup;
- текущие состояния loading, error, empty и success;
- работу списка избранного, который использует тот же каталог.

### Зачёт

Выполнено локально и в production без VPN. Дополнительная Network-проверка отсутствия клиентских запросов к `insforge.app` включена в финальный аудит этапа 10.

## Этап 9. Осознанно решить вопрос кэширования

### Baseline и принятое решение

- Production `/api/products` возвращает около `41.5 KB` JSON.
- Зафиксированы ответы без кэша примерно за `460 ms` и `934 ms`.
- В более медленном замере `841 ms` ушла на ожидание сервера и около `92 ms` на загрузку ответа: основная задержка находится в цепочке Vercel → InsForge, а не в размере JSON.
- Каталог планируется обновлять примерно раз в неделю порциями около 10 товаров; возможный объём — 100–200 товаров.
- Допустима задержка появления новых данных до трёх дней.
- Для `/api/products` выбран response cache Vercel CDN: три дня свежего кэша и один день stale-while-revalidate.
- Обычный Next.js `use cache` изучен, но не выбран: он требует включения `cacheComponents`, а его runtime-кэш по умолчанию хранится в памяти и может не сохраняться между serverless-инстансами. Для одинакового публичного JSON-ответа CDN-кэш является более прямой и проверяемой границей.

Планируемый заголовок успешного ответа:

```txt
Cache-Control: public, max-age=0, must-revalidate
Vercel-CDN-Cache-Control: public, s-maxage=259200, stale-while-revalidate=86400
```

Браузер не хранит ответ надолго, а Vercel может отдавать его с ближайшего edge-кэша. Ошибочные ответы `502` этим заголовком не кэшируются.

На первом проходе не добавлять «умное» кэширование: сначала добиться корректной работы и измерить запросы. Route Handler не участвует в React memoization, поэтому кэширование проектируется отдельно.

После рабочего варианта:

- измерить время ответа `/api/products` при холодном и повторном запросе;
- определить, как часто каталог меняется;
- изучить актуальный для Next.js 16 механизм Cache Components/`use cache` перед внедрением;
- выбрать допустимую свежесть данных;
- записать принятое решение, даже если решение — пока не кэшировать.

### Зачёт

Кэш появился только при измеримой пользе, а стратегия обновления данных понятна.

## Предполагаемые точки изменения

Точные имена уточняются во время реализации, но ответственность должна выглядеть так:

```txt
src/app/api/products/route.ts
  HTTP API для браузера

src/shared/api/insforge.server.ts
  server-only InsForge client

src/entities/product/api/insforgeProducts.server.ts
  server repository и запросы к базе

src/entities/product/api/products.ts
  клиентский fetch("/api/products")

src/features/products-catalog/model/useProducts.ts
  React lifecycle запроса, loading/error/retry
```

Необязательно механически принимать эти пути. Перед переносом нужно проверить FSD-границы и не создавать два конкурирующих источника истины.

## Не входит в этот roadmap

- перенос PostgreSQL в Vercel/Neon;
- возврат изображений в InsForge Storage;
- admin/API key в приложении;
- собственный Express/Nest.js сервер;
- авторизация и пользовательские записи в базу;
- Server Action вместо обычного read-only HTTP endpoint;
- преждевременный CDN или сложный cache invalidation.

## Definition of Done

- браузер не обращается к InsForge напрямую;
- сервер Vercel получает каталог из InsForge через anon key;
- изображения отдаются из `public/images/products`;
- production работает в России без VPN;
- ошибки upstream превращаются в понятный UI и безопасный HTTP-ответ;
- прямой read-only доступ по-прежнему ограничен RLS/grants;
- решение покрыто минимальными тестами и описано в README;
- я могу без подсказки объяснить весь путь данных от `useProducts` до строки PostgreSQL.
